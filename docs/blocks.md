# DPI GUI — заметки по блокам (базис знаний)

> Файл для технических фактов и «узлов встречи» смежных подсистем. Пунктов
> Spirit: фиксировать решения с обоснованием, чтобы не спорить по кругу.

## 1. DNS: системные адреса (Windows)

На Windows `from_system_conf()` корректен. Он не «угадывает» адрес, а читает те же
адаптеры через `ipconfig::get_adapters()`, но за счёт встроенного TCP-fallback
оказывается устойчивее голого nslookup. У пользователя в РФ, где TCP:53 часто
заблокирован полностью или оба протокола возвращают одинаковый ответ от ТСПУ,
`from_system_conf()` получит именно подменённый адрес. Менять `from_system_conf()`
на вызовы `cmd /c nslookup` было бы антипаттерном (§3.9) — текущий код на
trust-dns правилен.

## 2. DoH-сервисы: источники списков (SSOT-файл)

Список используемых DoH-резолверов живёт в
`src-tauri/defaults/doh-services.txt` (см. AGENTS.md §4.2: при каждом старте
копируется в `AppData/Roaming/DPI_GUI/defaults/doh-services.txt`). Формат файлов:
полный URL (`https://host/dns-query`) или только хост; комментарии `#` игнорируются.

> **ВАЖНО (РКН/ТСПУ):** ТСПУ банит IP-адреса DNS-серверов. Поэтому серверы из
> списков могут НЕ отвечать у пользователя, пока не добавлены в обход (winws).
> Не используйте «сервер не пингуется» как критий добавления в файл: проверку
> живости проводить только при включённом обходе (tests `live_doh_resolvers_*`
> в `site_probe.rs` игнорируются без сети по этой же причине).

### 2.1 Справочные источники
1. **AdGuard DNS KB — «Известные DNS-провайдеры»**
   https://adguard-dns.io/kb/ru/general/dns-providers/
   (таблица протоколов по провайдерам: IPv4/IPv6/DoH/DoT/DoQ/DNSCrypt;
   выбирать ВНИМАТЕЛЬНО unfiltered-варианты — фильтрующие ломают «тест подмены
   DNS»: часть доменов просто не резолвится).
2. **DNSCrypt — Public DNSCrypt & DoH Servers List**
   https://dnscrypt.info/public-servers/
   (страница рендерится с GitHub-репозитория
   https://github.com/dnscrypt/dnscrypt-resolvers — то же самое в markdown).

### 2.2 Хосты, добавленные из этих источников (23.10.2026)
В файл добавлены только unfiltered / без-логов публичные anycast-резолверы
(основание — 1 и 2 выше): `unfiltered.adguard-dns.com`, `cloudflare-dns.com`,
`dns.google`, `doh.sandbox.opendns.com` (OpenDNS Sandbox, unfiltered), `doh.dns.sb`,
`dns10.quad9.net` (unfiltered), `wikimedia-dns.org`, `doh.libredns.gr`,
`unfiltered.joindns4.eu` (DNS4EU, unfiltered), `dns.digitale-gesellschaft.ch`,
`dns.decloudus.com`. Итого 19 валидных строк (8 RU-специфичных + 11 глобальных).

Не добавлены намеренно:
- **ControlD** (`freedns.controld.com/p0`) — НЕСОВМЕСТИМ с нашим парсером:
  `parse_doh_services` отбрасывает путь, а запрос всегда идёт на
  `https://{host}/dns-query` (см. `main.rs:68`), кастомный path `/p0` потеряется.
  Если когда-нибудь понадобится — сначала менять формат файла парсер+путей.
- Китайские (`doh.360.cn`, `dns.alidns.com`, `dns.pub`) — гео-фон РФ бессмыслен.

- `dns.nextdns.io` — без ID-профиля режет рекламу по умолчанию.

## 3. Подбор DNS: критерий вердикта — только сквозная проба

**Кейс Patreon (01.11.26).** Старая эвристика dns_pick («IP вне диапазонов Google =
проксирует, рабочий») была хардкодом под единственный кейс (eu.geohide.ru отдаёт
свои шлюзы для Google). На patreon.com «ПРОКСИРУЕТ (РАБОЧИЙ)» получал даже честный
dns.google; юзер включал рекомендованный DNS — сайт не открывался, потому что его
режет **собственный гео-блок Patreon** (Cloudflare error 1009 «Access denied»),
а не DNS. Три слоя отказа, которые нельзя путать:

1. **DNS-отравление** — лечится DoH/сменой резолвера;
2. **DPI по SNI** (TLS рвётся, RST) — лечится обходом (winws);
3. **отказ самого сайта** (голый 403/451, страница сервиса «регион недоступен»)
   — лечится ТОЛЬКО VPN/прокси (смена исходного IP): DNS, hosts и обход бессильны.

**Инвариант:** вердикт «рабочий DNS» даётся только по сквозной HTTPS-пробе
(`site_probe::http_via_ip` — SSOT), а не по ownership IP-адресов. Эвристики вида
«IP принадлежит X ⇒ проксирует» запрещены: они верны ровно для одного сайта и лгут
на всех остальных. Классификация `dns_pick.rs`: `Gateway` (все IP — собственные
шлюзы DoH-сервиса через `DohAnswers.gateway_owner`) / `Resolves` (IP-пул
большинства: адреса, отданные ≥2 сервисами) / `Diverges` / `Dead`; проба — до 4
уникальных IP-сетов, агрегат по приоритету `Open > SiteBlocked > Unverified >
DpiBlocked > Unreachable`.

**Кейс SPA-оболочки (инцидент 08.11.26 — ложь «открывается» на aistudio).**
`http_via_ip` анонимно получал 200 от JS-оболочки SPA (aistudio welcome: 66 КБ
HTML, 36 байт видимого текста) без маркеров ограничения — вердикт Ok(200) →
«открывается», а ограничение этих сервисов рисуется JavaScript'ом **только после
входа в аккаунт**, анонимная проба его видеть не может. Теперь живая 2xx/3xx-
страница с видимым текстом меньше порога (константа `UNVERIFIED_MIN_VISIBLE` =
200 байт; замер 08.11.26 ДО прогона: aistudio=36, google.com=827, github.com=6800)
классифицируется как `HttpResult::Unverified` — «транспорт работает, доступность
после входа не подтверждена»; это отдельный честный вердикт (warn), а не «Open».
Подгонять порог после живых прогонов запрещено (core rules §1.11). Пробы честных
резолверов дрейфуют между прогонами (GeoDNS-сеты эджей меняются: 08.11.26
cloudflare-dns.com вернул чужой сет и честно получил Diverges) — эталон-тест
фиксирует только анти-ложь инвариант «не Open» и gateway_owner-инварианты.

**Чистое окно в dns_pick (08.11.26).** HTTP-пробы сайта идут при выключенном
обходе (`bypass_toggle::OffWindowGuard` вокруг `run_site_probes` в `run_pick`):
с включённым winws проба видит только «успех» и приписывает DNS то, что чинит
обход. Живость DoH и шлюзов, наоборот, мерится С обходом (§2). Факт
восстановления обхода пишется в лог.

**Шлюзы DoH-сервисов — только сквозная проба (правка 09.11.26):** раньше вердикт
шлюза ставился по TCP-живости («шлюз отвечает на :443»), а HTTP-проба шлюза была
запрещена из-за мины «шлюз отвечает 200» (кейс openrouter.ai/80.74.30.162 — свой
200 шлюза не является страницей сайта). TCP-правило само стало источником лжи:
TCP:443 отвечал, а сайт реально открывался только через 2 из 7 шлюзов пула
eu.geohide.ru (09.11.26 — юзер получил «Рабочий DNS», сайт в браузере не открылся).
Мина обезврежена архитектурой SSOT-пробы: `http_via_ip` валидирует TLS-сертификат
имени сайта — заглушка шлюза без валидного сертификата даёт честный `BadCert`, а
passthrough-фронтинг показывает оригинальный сертификат и настоящую страницу
(`Ok`). Теперь шлюзовые сеты проверяются сквозной пробой `http_via_ip` по каждому
IP пула (`aggregate_gateway_set` в dns_pick.rs): `GatewayAlive` — сайт открывается
через ≥ половины шлюзов; `GatewayPartial` — меньше половины (warn: «может не
открыться с первой попытки, надёжнее VPN»); ни один — `GatewayDead` либо
`SiteBlocked` (сайт отказывает и IP шлюза → VPN). Подтверждённые пробой IP
(`fronting_ips`) — SSOT для «Применить» во вкладке Браузер: маппинг берёт
проверенный шлюз, а не `resolved[0]` (в кейсе 09.11.26 это был мёртвый
37.221.93.128).

**Кейс посессионного гео-блока (aistudio):** живой Gateway остаётся рекомендацией
даже когда пробы честных резолверов дают SiteBlocked — блок привязан к исходному
IP и проявляется только после входа в аккаунт; фронтинг-шлюз — единственная
«DNS-мера» против него. Анонимная проба видит только JS-оболочку (Unverified):
если сайт ограничивает по региону после входа — смена DNS бессильна, честный
итог ведёт к фронтинг-шлюзу (🛰) или VPN.

**То же заземление в «Анализе сайта»:** фактовые пробы идут в чистом окне (обход
выключен) и честно видят RST — слой 2. Отказ самого сайта (слой 3) в чистом окне
НЕ виден: TLS ещё не проходит. Поэтому после восстановления обхода анализ делает
контрольную пробу главного домена по настоящему DoH-адресу
(`site_probe::bypass_on_control_probe`): `Forbidden/ServiceRestrict` → отчёт
печатает «САЙТ САМ ОГРАНИЧИВАЕТ (гео-блок/WAF, у Cloudflare — ошибка 1009): нужен
VPN», а `site_solution::decide` не советует починку (списки/hosts/DNS бессильны).
`BlockPage` отказом сайта НЕ считается (маркеры в теле — страница оператора).
